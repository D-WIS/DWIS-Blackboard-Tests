# Manifest library

Real manifests from the projects that wrote them, kept as they were written, each with the validation report the semantic service is expected to return for it (M4.F, Tests #21; the owner's direction of 17 November 2026: the SmartConnect manifest alone is not enough to test on). The library feeds the smoke (`compose/smoke.sh`, step 2c, through `tools/library/check-library.py`), the host tests of the Semantic repository, the conformance suite (R-MOD-3, M4.5) and later the DevKit material.

One folder per manifest:

- `manifest.json`: the manifest as its project wrote it (bytes unchanged, the byte-order mark included when it had one), except where the table says that names were replaced to keep the source anonymous.
- `expected-report.json`: the stable part of the report the service returns on the pinned vocabulary (`2026-10-14`): the HTTP status, the manifest id, `accepted`, the vocabulary version, the counts, the live parts and the findings sorted; not the timings and sizes. Recorded with `check-library.py --record` against the compose stack and reviewed by the owner; a difference on a later run is a test failure, and a change of the service or the vocabulary that changes a report is recorded again, on purpose, in the pull request that changes it.

The SmartConnect manifest and its edited copies stay in `fixtures/manifests/` as the "many issues" example and the standard ingest fixture; they are not part of the library.

The sizes and the "what is special" column come from a name scan against the vocabulary of 14 October 2026 (`tools/library/` has no scanner; the scan was a session script of 17 and 21 November 2026); the expected reports say what the service itself finds.

To add a manifest: a folder with `manifest.json`, a row here with its origin and licence, then `python3 tools/library/check-library.py --record` against a running stack (`FUSEKI_TAG=edge SEMANTIC_TAG=edge compose/smoke.sh --no-build`, or the compose stack on its own), review the report, commit both files.
